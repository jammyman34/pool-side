# Pool Side Architecture

_Last updated: August 2026_

## Overview

Pool Side is organized around a deterministic pool-management engine that converts current pool evidence, configuration, history, and treatment state into an explainable treatment workflow.

The architecture separates five major concerns:

1. Pool evidence and configuration
2. Chemistry interpretation
3. Treatment generation
4. Safety and swimability
5. Treatment workflow and verification

At a high level:

Pool Configuration
        │
        ▼
Pool Test / Effective Pool State
        │
        ├── Chemistry readings
        ├── Visual observations
        ├── Pool conditions
        ├── Evidence timestamps
        └── Historical context
                │
                ▼
        Chemistry Engine
                │
                ├── Pool Score
                ├── Treatment Generation
                ├── Watchlist
                ├── Recommendation Confidence
                └── Explanation Inputs
                        │
                        ├───────────────┐
                        ▼               ▼
              Swimability V2    Treatment Workflow
                        │               │
                        │        ├── Treatment Steps
                        │        └── Focused Check Steps
                        │               │
                        └───────┬───────┘
                                ▼
                        Treatment Plan UI
                                │
                                ├── Why This Plan
                                ├── Next Full Pool Test
                                ├── Notifications
                                └── External Review

Historical data feeds the system throughout this process.

Two services share the chemistry authority, and the split matters:

- **ChemistryPolicy** is the canonical authority for how a single reading is _classified_: its operating band, its action state, its correction disposition, and whether it blocks swimming. It is sanitizer-aware (TA bands differ between hypochlorite and acidic/stabilized chlorine) and surface-aware (CH bands differ by surface type). ChemistryPolicy owns the numeric ranges.
- **ChemistryEngine** is the authority for what to _do_ with those classifications: treatment generation, dose calculation, application policy, suppression, watchlists, Pool Score, and explanation inputs. Where ChemistryEngine needs to decide whether a value is in range, it consults ChemistryPolicy rather than carrying its own duplicate bands.

UI components display and interact with this engine output rather than independently interpreting pool chemistry. When these two documents and the code disagree, the code is authoritative; see the Source-of-Truth Authorities table below.

# Core Data Models

## PoolConfiguration

PoolConfiguration represents relatively persistent characteristics of the pool.

Examples include:

- pool volume
- pool type
- surface type
- saltwater status
- chlorine product preference
- pH increaser preference
- pH decreaser preference
- alkalinity increaser preference
- calcium increaser preference
- stabilizer preference
- default test method
- robotic cleaner
- pets
- pool cover

Configuration describes the pool.

It should change relatively infrequently compared with PoolTest data.

---

## PoolTest

PoolTest represents observed pool evidence at a point in time.

A traditional full PoolTest contains:

- FC
- CC / TC
- pH
- total alkalinity
- calcium hardness
- CYA
- salt when applicable
- visual indicators
- pool conditions
- notes
- score
- timestamp
- associated treatment information

PoolTest also supports focused verification evidence generated by treatment workflow Check steps.

A focused check does not represent a new complete measurement of every chemistry parameter.

For this reason, PoolTest also maintains:

- per-parameter evidence timestamps
- focused-check metadata
- information identifying which chemistry values were newly measured

This prevents a focused FC/CC check, for example, from making an older pH, TA, CH, or CYA measurement appear newly tested.

---

# Effective Pool State

The engine may need to reason from chemistry values measured at different times.

The effective pool state therefore combines the newest valid evidence for each parameter rather than assuming every chemistry value has the timestamp of the newest PoolTest record.

Example:

A full test at 10:00 AM measures:

- FC
- CC
- pH
- TA
- CH
- CYA

A focused FC/CC verification occurs at 11:00 AM.

The effective state at 11:00 AM contains:

- FC evidence: 11:00 AM
- CC evidence: 11:00 AM
- pH evidence: 10:00 AM
- TA evidence: 10:00 AM
- CH evidence: 10:00 AM
- CYA evidence: 10:00 AM

This mixed-age evidence model is important for both treatment generation and swimability.

Focused testing must never implicitly refresh unmeasured chemistry.

---

# PoolConditions

PoolConditions describe events that occurred since the previous relevant test.

These are contextual evidence rather than chemistry.

Current examples include:

- swimming
- pet swimming
- rain
- cover open time
- organic debris
- skimming
- vacuuming / robot cleaning
- brushing
- water added
- backwashing

Where applicable, conditions distinguish between:

- Unknown
- Explicitly absent
- Present

Unknown means the user did not provide evidence.

Explicit absence means the user confirmed the condition did not occur.

This distinction affects recommendation confidence.

---

# ChemistryPolicy

ChemistryPolicy is the single canonical authority for classifying an individual chemistry reading.

Given a parameter, a value, and a context (sanitizer type, surface type, salt configuration, measurement resolution), it returns a classification containing:

- an action state: actNowLow, recommendedLow, ideal, recommendedHigh, actNowHigh
- a correction disposition (what, if anything, should be done)
- whether the value blocks swimming

Key properties:

- Operating bands live here, not scattered across the engine. Representative bands include CYA 30–50 (target ~40), CH 200–400 for plaster, and pH ideal 7.2–7.6 with swim-blocking only at the extremes.
- TA is sanitizer-aware: hypochlorite pools use roughly an 80–100 ideal band (target ~90), while acidic/stabilized-chlorine pools use roughly 100–120 (target ~110).
- CH is surface-aware, so plaster and vinyl are classified differently.
- Salt ranges are configurable to the specific chlorine generator rather than assumed universal.

ChemistryPolicy contains no presentation logic and no dosing logic. It answers only "what state is this reading in, and does it block swimming?" Every other subsystem — treatment generation, Pool Score, Swimability V2, Next Full Pool Test — consumes this classification instead of re-deriving ranges.

---

# ChemistryEngine

ChemistryEngine is responsible for interpreting pool chemistry.

Its responsibilities include:

- chemical evaluation
- free-chlorine policy classification and treatment targeting
- treatment generation
- treatment suppression
- product selection
- dose calculations
- application limits
- conflict avoidance
- pool score (using ChemistryPolicy to decide which readings are in range)
- watchlists
- recommendation confidence inputs
- historical analysis
- trend analysis
- explanation inputs

ChemistryEngine must not contain presentation logic.

It should produce deterministic domain results that other systems can interpret and display.

---

# Treatment Generation

Treatments are generated from current effective pool state, configuration, and history.

Conceptually:

Effective Pool State
        │
        ▼
Chemical Evaluation
        │
        ▼
Candidate Treatments
        │
        ▼
Conflict / Safety Evaluation
        │
        ▼
Treatment Validation
        │
        ▼
Suppression / Deferral
        │
        ▼
Application Policy
        │
        ▼
Final Treatment Recommendations

Treatment generation may:

- generate required corrective treatments
- generate optional maintenance treatments
- suppress unnecessary treatments
- defer conflicting treatments
- limit a current application while retaining total calculated demand
- recommend monitoring instead of treatment
- generate nonchemical actions
- require verification before additional treatment

Treatment generation should solve the current problem without unnecessarily creating another one.

---

# Treatment Application Policy

Calculated chemical demand and the amount appropriate for one application are not always the same.

For products where staged dosing is safer, Pool Side separates:

- total calculated correction
- current recommended application

For example, acid demand may exceed the amount that should be added in one application.

The workflow should recommend the conservative current application, require appropriate circulation and verification, then reassess before recommending another dose.

The engine must not assume that a mathematically calculated total dose should always be applied at once.

---

# Treatment Classification

Treatment recommendations are classified by their role in the workflow.

Important classifications include:

- swimBlocking
- poolCare
- nonChemicalAction

Treatments may also have urgency such as:

- immediate
- recommended
- optional

Treatment classification is separate from the underlying chemistry problem.

A treatment can be optional pool maintenance without preventing swimming.

A corrective treatment can require completion and verification before the pool is considered ready.

---

# Treatment Lifecycle

Treatments are stateful.

Relevant states include concepts such as:

- planned
- waiting
- verification required
- completed
- skipped
- unresolved recovery action

Treatment state affects:

- workflow progression
- swimability
- verification
- notifications
- future treatment generation

Skipped treatment instances remain part of history.

Skipping a treatment does not create a permanent preference to suppress that treatment.

If later evidence shows that the treatment is still needed, the engine may generate a new treatment step.

---

# TreatmentWorkflowEngine

TreatmentWorkflowEngine converts treatment recommendations into an ordered user workflow.

The workflow contains two primary step types:

1. Treatment
2. Check

Example:

1. Add liquid chlorine
2. Check FC & CC
3. Add muriatic acid
4. Check pH

Only the currently actionable step should be interactive.

Later steps remain visible and readable so users can understand and prepare for what comes next.

Future steps are visually inactive without obscuring their content.

---

# Focused Check Steps

Check steps are first-class workflow objects.

They represent treatment-specific verification rather than another full pool test.

Examples include:

- Check FC & CC
- Check pH
- Check TA
- Check CYA
- Check CH

Check timing comes from the treatment and verification policy.

Examples:

- chlorine: after circulation
- acid: after the required pH correction interval
- alkalinity: after the alkalinity circulation interval
- CYA: after the stabilizer verification interval
- calcium: after the calcium verification interval

A Check becomes actionable when its parent treatment and timing requirements have been satisfied.

---

# Focused Check Completion

Completing a Check opens focused test entry for only the parameters required by that Check.

Saving the focused result:

1. records new evidence for the measured parameter or parameters
2. preserves the previous evidence timestamps for unmeasured chemistry
3. updates the effective pool state
4. reassesses safety
5. reruns production recommendation generation
6. rebuilds the unfinished portion of the treatment workflow

This makes verification part of the treatment-management loop rather than a passive reminder.

---

# Check Completion Authority

A focused Check step reaches a completed state through exactly **one** path: the user opens the Check, enters the required parameter(s), and saves the measured result (`saveFocusedCheck`). Its `checkResultTestID` then points at the Check's own originating test.

There is deliberately **no automatic completion**. In particular, a later complete pool test does **not** verify or complete a pending Check — even if that test measures the Check's parameter after the Check's due time. Logging a full test does not prove the user actually performed the treatment's follow-up measurement, so the purple Check card stays unchecked until the user checks it. (An earlier "full-test supersession" mechanism was removed for exactly this reason.)

No other action completes a Check. In particular:

- Generic "mark treatment complete" does not complete a Check step.
- Marking a Check incomplete is rejected; a Check is not a manually toggled treatment.
- The passage of a Check's due time does not complete it — the reminder fires, but the Check remains pending.
- Skip and Restore are rejected at the ViewModel boundary when the target is a completed or inapplicable Check. The boundary returns a typed result (applied, rejectedCompleted, rejectedSuperseded, rejectedInapplicable) so the UI can disable the gesture and the ViewModel can refuse the state change consistently.

These guards exist because a Check carries verification evidence. Allowing an ad-hoc skip/restore/uncomplete on an already-completed Check would silently corrupt the evidence chain and could make an unsafe pool appear verified.

---

# Workflow Reassessment

A focused Check can change what should happen next.

When new focused evidence is entered:

Completed or skipped prior steps
        │
        └── Preserved as history

Current Check
        │
        └── Stores new evidence

Unfinished future generated steps
        │
        └── Removed / invalidated

Updated Effective Pool State
        │
        ▼
Chemistry Engine Reassessment
        │
        ▼
New Future Workflow

The engine reassesses the pool from the point where new evidence was introduced.

Future treatments may:

- remain
- disappear
- change dose
- change order
- be replaced
- be newly introduced

Safety and chemistry determine the new sequence.

Previous future recommendations are not treated as commitments.

---

# Swimability V2

Swimming readiness is evaluated independently from Pool Score.

Pool Score represents overall pool health.

Swimability V2 answers a different question:

> Based on the evidence currently available, is the pool ready for swimming?

Important readiness gates include:

- sanitizer adequacy
- pH
- combined chlorine
- water clarity
- visible algae
- evidence freshness
- treatment completion
- circulation requirements
- product re-entry restrictions
- required verification

Possible user-facing states include concepts such as:

- Ready to Swim
- Do Not Swim
- Test Before Swimming
- Expected Ready Around a Time
- More Information Needed

A good Pool Score does not override a failed safety gate.

---

# Evidence Freshness

Swimability depends not only on chemistry values but also on how recent the supporting evidence is.

Evidence freshness is evaluated using parameter-specific timestamps.

A focused test refreshes only the parameters actually measured.

This prevents a new FC reading from incorrectly making stale pH or other chemistry appear current.

When required evidence becomes too old, Swimability may require new testing even if the last known value was acceptable.

---

# Historical Processing

The engine receives historical PoolTests through recent history.

History is used for:

- repeated chlorine failures
- chlorine loss patterns
- treatment suppression
- recommendation confidence
- trend detection
- pH trend behavior
- historical stability
- completed treatment context

History must be rebuilt from persistent records.

Deleted tests must not continue influencing calculations.

---

# Pool Score

Pool Score describes overall pool condition. It is explicitly not a swimming-safety decision — Swimability V2 owns swimming readiness, and a good score never unlocks a failed safety gate.

There is one canonical score API. Production reads Pool Score through `PoolViewModel.scoreAssessment(for:in:)`, which delegates to `ChemistryEngine.scoreAssessment(...)` with the previous test, recent history, and the real pool configuration. The result is a structured `PoolScoreAssessment` containing:

- `score` — the numeric 0–100 value
- `grade` — the human-facing band label (via `ChemistryEngine.scoreGrade(for:)`)
- `drivers` — the canonical, ChemistryPolicy-classified reasons the score is not perfect

Inputs may include chemistry, visual indicators, historical behavior, pool conditions, contextual penalties, and safety floors.

Authority alignment: whether a reading counts as "in range" for scoring is decided by ChemistryPolicy, not by a second set of bands inside the score model. This resolves earlier drift where the score's own TA/CH ranges disagreed with policy. The score's tuned penalty magnitudes are preserved; only the in-range determination is delegated to policy.

`PoolTest.overallScore` remains as a convenience accessor for lightweight/preview use only — it assumes the current configuration and no history. Production surfaces must use `PoolViewModel.scoreAssessment` / `overallScore` so the score reflects real configuration and history and never leaks `PoolConfiguration.current`.

---

# Recommendation Confidence

Recommendation confidence estimates the quality of evidence supporting the recommendation.

Inputs include:

- chemistry evidence
- pool conditions
- visual observations
- history
- treatment history
- missing or unknown information

Confidence may be:

- increased by explicit observations and useful history
- reduced by missing or uncertain evidence

Confidence must never weaken safety rules.

It primarily affects explanation and communication.

---

# Watchlist

Not every undesirable condition requires immediate treatment.

Watchlist items represent conditions that should be observed rather than acted on immediately.

Examples include:

- elevated TA with acceptable pH
- manageable but elevated CYA
- pH likely to drift because of alkalinity
- cover-management concerns
- scaling risk

Watchlist items are not workflow actions unless the engine explicitly promotes them into a treatment or nonchemical action.

---

# Why This Plan

Why This Plan explains the current recommendation.

It may include:

- summary
- recommendation confidence
- key factors
- expected outcome
- important suppressed recommendations
- treatment rationale

It should explain why the engine chose the current plan, including why something was intentionally not treated.

---

# Next Full Pool Test

The Next Pool Test system is intentionally separate from focused treatment verification.

The global card represents only:

> The next full routine pool test.

It should never be used to represent a focused FC/CC, pH, TA, CYA, or CH verification.

Treatment-specific verification belongs in Treatment Workflow Check steps.

The routine testing engine may use:

- current pool stability
- treatment activity
- recent chemistry
- demand
- historical behavior

to determine when the next complete pool test should occur.

---

# Notifications

Notifications can represent different kinds of events.

Examples include:

- a Check step becoming ready
- treatment verification timing
- the next full routine pool test

Notification copy should preserve this distinction.

A targeted verification should identify its parameters, such as:

- Retest FC/CC
- Retest pH
- Retest TA
- Retest CYA
- Retest CH

A routine notification should clearly refer to the full pool test.

## Check-Owned Verification Reminders

A focused Check step owns its own verification reminder. The lifecycle is:

- When the parent treatment is completed, the Check's reminder is scheduled for the moment the Check becomes actionable (parent completion time plus the parameter's verification/circulation delay). The scheduled identifier is stored on the Check as `checkReminderNotificationIdentifier`.
- If the Check is completed (by the user) or its workflow is removed (including by deletion), that reminder is cancelled. State transitions cancel the notification rather than leaving it to fire.
- The reminder is a nudge to *perform* the follow-up test; it does not complete the Check. When it fires, the Check stays pending until the user enters the result.
- The reminder is not re-scheduled on every recompute, so a still-pending Check does not repeatedly re-nag.

This keeps the notification bound to the piece of state it represents, so notifications cannot outlive the Check that owns them.

# AIService and External Review

AIService is intentionally separate from ChemistryEngine.

Responsibilities include:

- preparing structured summaries
- preparing external-review exports
- exposing recommendation confidence
- exposing treatment rationale
- supporting future AI integrations

The deterministic production engine remains authoritative.

AI may review, explain, or critique recommendations.

AI must not silently replace deterministic chemistry or safety logic.

# Insights

Insights interpret historical pool behavior.

Current responsibilities include:

- Pool Personality
- What's Changing
- Testing Rhythm
- Pool Score Trend
- Chemical Trends

Insights should focus on patterns rather than today's treatment decisions.

---

# Dashboard

Dashboard presents current pool state.

Responsibilities include displaying:

- current score
- current chemistry
- swimability
- active treatment workflow
- next full pool test
- recent history

Dashboard should consume engine and workflow output rather than independently calculate chemistry recommendations. It does not compute swim readiness inline; it displays Swimability V2's result.

The treatment workflows shown on the Dashboard are derived through `PoolViewModel.dashboardWorkflows(from:)`, which partitions the pool's workflows into two groups:

- **active** — workflows with an outstanding actionable step (a treatment to perform or a Check to complete)
- **completed** — workflows whose steps are all resolved (completed or skipped)

Each entry is a `DashboardWorkflowItem` keyed by its originating (root) test. When the latest test is deleted, the Dashboard falls back to the next valid workflow rather than showing a dangling reference.

---

# Deletion and Recalculation

Deleting historical evidence can invalidate downstream conclusions.

Deleting a PoolTest should cause affected state to be rebuilt as though that test never existed.

Depending on downstream dependencies, this may include:

- removing associated treatments
- removing associated Check evidence
- canceling related notifications
- rebuilding chronological history
- regenerating affected treatment plans
- rebuilding effective chemistry state
- recalculating Swimability
- recalculating Next Full Pool Test
- refreshing Dashboard
- refreshing Insights
- refreshing trends
- refreshing recommendation confidence

Persistent derived state must not continue referencing deleted evidence.

Deletion is handled by a single orchestration path (`PoolViewModel.deletePoolTestAndRefreshHistory`) so these steps cannot be applied inconsistently.

Because a Check is completed only by the user's own focused result, its `checkResultTestID` always points at its own originating test. Deleting that test cascade-removes the Check with it, so no surviving Check can ever reference a deleted result test — there is no "falsely verified Check" to repair.

Orphaned reminders are still cancelled as part of deletion: Check-owned verification reminders and the routine Next Full Pool Test reminder. Deleting the last remaining test cancels the routine reminder rather than leaving it scheduled against no pool state.

This state survives relaunch: the rebuilt records are what persist.

---

# Backward Compatibility

Older saved treatment plans may contain treatment steps without explicit workflow Check steps.

The application should continue rendering these plans safely.

Newly generated or recalculated plans should use the current TreatmentWorkflowEngine model.

Migration should preserve user history whenever possible.

---

# Testing Architecture

Pool Side uses automated scenario validation in addition to targeted unit tests.

The scenario catalog exercises production behavior across areas including:

- chlorine
- combined chlorine
- pH
- alkalinity
- calcium
- CYA
- salt
- acid products
- dry chlorine
- conflicting chemistry
- multiple treatments
- evidence freshness
- uncertainty
- historical behavior
- volume scaling
- magnitude sanity checks
- application policy
- Next Pool Test behavior
- treatment workflow

Scenario fixtures must reproduce production conditions faithfully.

A failing scenario must not automatically be treated as a production bug.

Failures should be classified as:

A. production defect
B. fixture does not faithfully reproduce production conditions
C. stale or incorrect test expectation

Production logic should only change for category A failures.

# Source-of-Truth Authorities

When a question has more than one plausible owner, exactly one subsystem is authoritative. The others consume its output.

| Question | Authoritative owner | Notes |
| --- | --- | --- |
| What operating band / action state is a reading in? Does it block swimming? | ChemistryPolicy | Sanitizer-aware TA, surface-aware CH, configurable salt. |
| What treatment (if any), what dose, in what order? | ChemistryEngine + TreatmentWorkflowEngine | Engine generates and doses; workflow orders and gates. |
| Is the pool ready to swim right now? | Swimability V2 | The only readiness authority. Pool Score never decides this. |
| What is overall pool condition (score / grade / drivers)? | `PoolViewModel.scoreAssessment` → `ChemistryEngine.scoreAssessment` | Returns `PoolScoreAssessment`. In-range determination delegated to ChemistryPolicy. |
| Which chemistry value is the "current" one for a parameter? | Effective Pool State | Newest valid per-parameter evidence; mixed-age; provenance preserved. |
| When does a Check become actionable, and is it complete? | TreatmentWorkflowEngine + Check Completion Authority | Completes only via the user's saved focused result. No automatic completion. |
| Should Skip / Restore / uncomplete apply to a Check? | `PoolViewModel.focusedCheckTransitionRejection` | Typed rejection shared by UI and ViewModel. |
| When is the next full routine pool test? | NextTestRecommendationEngine | Separate from focused verification; always means a complete panel. |
| Which treatment reminder / verification reminder fires? | The owning Check (Check-owned notifications) | Scheduled at parent completion; cancelled on completion/supersession/deletion. |
| What survives deleting a test? | `deletePoolTestAndRefreshHistory` | Reopens falsely verified Checks; cancels orphan reminders; rebuilds history. |
| What does the Dashboard show as active vs completed work? | `PoolViewModel.dashboardWorkflows` | Partitions workflows; consumes engine output, computes no chemistry. |

When this document and the code disagree, the code is authoritative and this table should be corrected.

# Open Limitations

Documented honestly so they are not mistaken for solved problems:

- **No product-label database.** Product suitability and staged-dosing behavior are encoded in engine logic, not looked up from a maintained catalog of real product concentrations. There is one calcium product (Calcium Chloride); calcium is raised, not repriced across alternatives.
- **Salt ranges are user/generator-configured**, not inferred. If the configured range is wrong, salt classification will follow the configured range.
- **Weather is not yet an engine input.** Long-term intelligence anticipates it, but current recommendations do not consume forecast or observed weather. (Weather-related UI/persistence work is tracked separately.)
- **`PoolTest.overallScore` is a convenience accessor** that ignores history and assumes current configuration; it is not the production score authority.
- **Backward-compatible legacy plans** may lack explicit workflow Check steps and are rendered without regenerating unless recalculated.

# Architectural Rules

When adding new behavior, first determine whether it belongs to:

- PoolConfiguration
- observed pool evidence
- ChemistryEngine
- Swimability
- TreatmentWorkflow
- scheduling / notification
- presentation

Do not allow these responsibilities to collapse into one another.

---

# Avoid

- UI decisions inside ChemistryEngine
- duplicated chemistry calculations
- treating Pool Score as swim safety
- treating a focused Check as a complete PoolTest
- refreshing unmeasured chemistry timestamps
- generic verification when the required parameter is known
- cached historical conclusions that survive deleted evidence
- hidden treatment state
- unexplained magic numbers
- AI-generated chemistry replacing deterministic production rules

---

# Prefer

- deterministic calculations
- recomputation from evidence
- parameter-specific evidence timestamps
- explicit treatment state
- explicit workflow ordering
- explainable recommendations
- conservative dosing
- staged treatment where appropriate
- focused verification
- history-aware decisions
- modular single-purpose services
- automated scenario validation

---

# Long-Term Direction

Pool Side is intended to evolve from:

"Analyze today's pool test."

to:

"Understand and manage my pool."

That requires more than increasingly complicated single-test rules.

The architecture should progressively improve its understanding of:

- how quickly this pool consumes chlorine
- how its pH tends to drift
- how weather and cover use affect it
- how treatments perform in this pool
- when the user really needs to test
- which conditions are normal for this pool
- when unusual behavior requires intervention

Personalization must remain subordinate to chemistry safety.

The system should become increasingly individualized without becoming opaque.

The core architectural principle remains:

Use current evidence, historical evidence, and explicit treatment state to make conservative, deterministic, explainable pool-management decisions.
